# Datadog container evidence

Datadog is the optional Kubernetes and container evidence source for incident investigation. The incident service uses Datadog's read-only [v2 timeseries query API](https://docs.datadoghq.com/api/latest/metrics/query-timeseries-data-across-multiple-products/) with a service-access bearer token that has `timeseries_query` permission. It queries three fixed [Kubernetes metrics](https://docs.datadoghq.com/containers/kubernetes/data_collected/): container restarts, memory working set and CPU usage. This does not duplicate Prometheus business SLI monitoring or Jaeger trace flow.

For a persisted development or staging incident, the query covers the selected 2-, 24- or 72-hour detection window, beginning fifteen minutes before detection and ending no later than now. It filters by the incident's `env` and `service` tags and groups by environment, service, Kubernetes namespace and pod name. Returned tags are rechecked before the browser receives any samples. The response is capped at 256 KiB, 48 source series and 240 timestamps; the UI shows at most four pod series per metric and labels the list when limited. Empty data means no matching measurements, not healthy infrastructure. A restart or high memory measurement is a lead, not proof of OOM or root cause.

The default Compose stack leaves Datadog unconfigured. To opt in, put a scoped bearer token in a private file outside the repository, set `DATADOG_TOKEN_PATH` to that path, and set `DATADOG_METRICS_URL` to your account's HTTPS `/api/v2/query/timeseries` endpoint. Then use `docker compose -f compose.yaml -f infrastructure/datadog/compose.yaml config --quiet` and deploy the incident service with that overlay. The service rejects embedded URL credentials, query strings, redirects and non-HTTPS endpoints outside local loopback tests. Tokens and vendor error bodies are never returned to the browser.

Local protocol tests prove request shape, bounded parsing and environment isolation. They do not prove Datadog account access, Agent collection, standard `env`/`service` tagging or a real Kubernetes incident. A vendor verification must produce a known pod restart or resource change in an isolated cluster, find the same pod and time in Datadog, and compare the incident panel's samples with the vendor source. The full flagship demonstration still requires real Splunk, Dynatrace and Datadog evidence when those systems are available.
