# Evaluation deployment promotion

The [Jenkinsfile](../infrastructure/jenkins/Jenkinsfile) separates deployment operations from GitLab's build and quality pipeline. Its actions are `DEPLOY`, `ROLLBACK`, and `SMOKE` for `DEV`, `STAGING`, and an isolated `PRODUCTION_LIKE` evaluation target. **PRODUCTION_LIKE is not a customer-facing production environment.** The Go executables still require `APP_MODE=local`, local-account auth is not SSO, and the chart's production-like values use staging incident data scope.

Jenkins needs a trusted agent labeled `telcopulse-deploy` with Bash, Helm 3.22, kubectl, jq, curl, base64, and Docker CLI. It needs private connectivity to the cluster and registry. Configure credentials with IDs `telcopulse-evaluation-kubeconfig` (secret file containing only evaluation contexts) and `telcopulse-registry-read` (read-only registry username and token). Configure non-secret job environment variables `REGISTRY_HOST`, `IMAGE_PATH`, `KUBE_CONTEXT_DEV`, `KUBE_CONTEXT_STAGING`, and `KUBE_CONTEXT_PRODUCTION_LIKE`. The Jenkins job must use the reviewed repository checkout, restrict who can start and modify it, and keep its deploy identity limited to the three evaluation namespaces. Its Kubernetes identity must be allowed to read the runtime Secret and open a port-forward to deployment-service in each target namespace, in addition to the existing Helm, Deployment and exec permissions. Create each namespace, `telcopulse-runtime` Secret, matching ingress TLS Secret, and a `telcopulse-registry-pull` Docker registry pull Secret before running the job; see the [Kubernetes deployment guide](kubernetes.md). The pull Secret is referenced by the Helm release, never copied from Jenkins into pod specs.

For `DEPLOY`, supply the full 40-character commit SHA published by a successful protected GitLab pipeline. Jenkins first checks the target and all ten remote image manifests without mutating the release, then presents the concrete image SHA for approval on the production-like evaluation target. The deployment repeats preflight to guard against changes during approval. It pins the chosen context and namespace, invokes `helm upgrade --install --atomic --wait` with the matching values profile and image tag, waits for exactly ten TelcoPulse Deployments to be Available, then makes an in-pod web request and checks that the gateway reports protected mode. A failed Helm upgrade rolls back through Helm's atomic behavior; a failed post-upgrade smoke restores the previous revision and checks it again. On a first install with a failed smoke, the script removes the failed release.

For `ROLLBACK`, supply an existing positive Helm revision from `helm history telcopulse` in that namespace. Jenkins checks the target, current release and requested history revision before any production-like approval. The script waits for rollback and repeats the smoke check; if that smoke fails, it attempts to restore the revision active before the rollback and checks again. `SMOKE` performs the availability and protected-route checks without registry credentials. Jenkins serializes runs of this job to avoid overlapping release mutations.

After a successful deploy, the script verifies that all ten running images have the requested full SHA and reports one `Completed` event per service to deployment-service. A successful rollback reads the ten running image tags and reports them as a new completed rollback operation, with `ci:jenkins-rollback` as actor and `rollback-rev-N` as version. These records become available to the deployment timeline and incident correlation. The trusted runner obtains the existing `SERVICE_TOKEN` from the namespace Secret, opens a localhost-only port-forward, and sends the token as a private curl header file. Helm's revision and last-deployed time supply stable event identity and timestamps across reporting retries for the same release. Preflights and smoke-only actions never report events. A reporting failure fails the Jenkins operation even if the Helm release is healthy, so an operator must inspect and reconcile the timeline; the script does not automatically roll back a healthy release for an observability reporting failure. A post-upgrade or post-rollback smoke failure is reported as `Failed` after restoration succeeds; Helm failures before smoke may have no reachable deployment-service and remain unreported.

Rollbacks affect Kubernetes resources and images, **not PostgreSQL migrations or business data**. Migrations must stay backward compatible with the previous app revision; schema or data recovery requires a separate reviewed procedure. Health checks do not prove a full purchase or incident lifecycle, external observability vendor availability, or disaster recovery. No live Jenkins or cluster run has been performed here.

Run `bash tests/ci/promote-release.sh` locally for a no-cluster contract test using fake Helm, kubectl, Docker and curl commands. It checks invalid tags and incomplete image sets before Helm, read-only preflights, successful promotion and smoke commands, ten per-service event payloads for successful and smoke-failed operations, SHA mismatch rollback, a reporting failure without an unnecessary rollback, explicit rollback, smoke-only mode, and the isolated production-like namespace mapping. It does not validate RBAC, image pulls, hooks, ingress routing or OpenShift SCC admission.
