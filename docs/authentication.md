# Operator authentication foundation

The independent Go `auth-service` owns `auth.users`, `auth.sessions`, and append-only `auth.events` in migration 017. It is reachable only on the Compose `internal` network and its `/internal/auth/*` endpoints require the existing service bearer token. Prometheus scrapes its health and metrics; the service does not have a host port. It currently runs only with `APP_MODE=local`.

Run `scripts/init-env.sh` once to create an ignored, mode-0600 `.secrets/local-admin-password`. After building the migration and auth-service images and starting Compose, run `scripts/bootstrap-auth.sh`. The script pipes the password to a one-time command inside the container; the credential is not in an image layer, Docker environment variable, or command argument. It creates `local-admin` as Administrator only if the user table is empty. Repeating bootstrap does not rotate or overwrite an existing account. Keep the private file available until gateway login is wired, and protect it like any local administrator credential.

The internal login endpoint verifies bcrypt cost-12 password hashes and returns one 256-bit random opaque session token to its authenticated service caller. PostgreSQL stores only its SHA-256 hash, issue time, expiry after eight hours, and optional revocation time. Validation reads current user role and active status on each call, so role changes and deactivation take effect without minting a new token. Logout revokes one token and is idempotent. Five failed known-account attempts lock it for fifteen minutes; the same generic 401 response is used for unknown accounts, wrong passwords, and a locked account. Authentication events include bootstrap, login success/failure/lock, and logout; an ordinary SQL trigger rejects update or deletion of those events. Database administrators remain outside this immutability guarantee.

`tests/integration/auth_internal.py` exercises the live service and PostgreSQL: service-token rejection, generic bad login, audit immutability, hashed-at-rest session, live role/active checks, revocation, lockout, and recovery. The test restores the administrator's role, active state, and lockout state in `finally` blocks and prints no password or token.

The gateway now has an **opt-in** operator boundary. Set `AUTH_REQUIRED=true` for the gateway and supply `AUTH_URL` plus the exact `WEB_ORIGIN`. `POST /api/v1/auth/login` accepts JSON credentials, exchanges them with auth-service, and returns only the user profile and an HttpOnly, SameSite=Strict, eight-hour maximum cookie. HTTPS origins also set Secure. `GET /api/v1/auth/me` returns the current validated user; `POST /api/v1/auth/logout` revokes the session and clears the cookie. Every other `/api/v1/` call validates the cookie against auth-service and reads the user's current role. Unsafe requests require an exact Origin match. Authentication outages return 503, invalid or revoked sessions return 401, and forbidden role actions return 403. The internal auth token is never sent to the browser.

The current gateway role policy allows all five roles to read. Viewer cannot mutate; Engineer or Administrator can start and stop simulations and reprocess quarantined notification events; Operator, Incident Commander, or Administrator can create incidents. Operator may acknowledge, assign, update investigation details, and append evidence on an active incident. Incident Commander and Administrator may also change severity, edit action items, resolve or reopen incidents, and write postmortem details. The incident service checks these field permissions against the locked current revision in the update transaction, so a forbidden change cannot alter the incident or its audit history. A validated operator ID and role are passed to incident-service over the service-authenticated call; neither is accepted from browser headers. The gateway also forwards the validated identity for simulation start/stop and notification reprocessing; each domain service checks the paired actor and Engineer/Administrator role headers before recording the operator ID in its immutable audit. The console queries `/api/v1/auth/status`, shows a login form when protected mode is enabled, displays the validated username and role, and clears its operator cache on sign-out or a rejected session. It presents only permitted mutation controls; the server check remains authoritative. Browser tests cover login, logout, Viewer presentation, a live Operator edit/denial flow and a live Engineer simulation audit.

To try protected mode locally after bootstrapping the account, start the stack with `AUTH_REQUIRED=true` and use the configured `WEB_ORIGIN` address in the browser (for example `http://localhost:3000` with the default port). Sign in as `local-admin` using the private `.secrets/local-admin-password` file. If the stack is already running, recreate the gateway with `AUTH_REQUIRED=true docker compose up -d --no-deps api-gateway`; recreate it with `AUTH_REQUIRED=false` to return to the default demo mode. The cookie is scoped to the browser host and all unsafe requests require the exact configured Origin, including the port.

The local unprotected mode remains the Compose default so the existing demonstration and bootstrap sequence keep working; in that mode incident, simulation and notification replay audit record `local-operator`. Incident, simulation and notification replay mutations require their own generated `INCIDENT_OPERATOR_TOKEN`, `SIMULATION_OPERATOR_TOKEN` or `NOTIFICATION_OPERATOR_TOKEN` in addition to `SERVICE_TOKEN`. Only the gateway and the corresponding domain service receive each mutation token. Payment and notification services retain shared-token access to simulation decisions and reads but cannot start or stop operator runs; a sibling holding only `SERVICE_TOKEN` cannot create or edit incidents or reprocess quarantined events. The gateway supplies the capability on operator requests in either demo or protected mode. This remains a local-only service boundary: internal HTTP is not mutually authenticated or encrypted, the token values are environment-backed, and rotation is not implemented. `APP_MODE=local` remains required; the local HTTP cookie lacks Secure, and SSO is not configured.

## Local administrator account management

In protected mode, only Administrator can use **Settings → Operator accounts**. `GET /api/v1/auth/users` lists local accounts in 50-item keyset pages; `POST /api/v1/auth/users` creates an account with an administrator-supplied initial password of 16–72 bytes; `PATCH /api/v1/auth/users/{id}` changes its role or active state. The public gateway requires the validated Administrator session and exact same-origin proof for mutations. Auth-service independently checks the current session against PostgreSQL before each operation; it does not accept a caller-supplied role. Responses never contain a password or hash.

Migration 018 extends append-only `auth.events` with the acting administrator and JSON details for creation, role and activation changes. Deactivation revokes existing sessions in the same transaction. A serialized database guard rejects changes that would remove the last active Administrator. Current-role checks already make demotions effective on the next request. The local test account can be managed without changing the one-time bootstrap credential.

This flow manages local accounts and roles only. Password reset, external identity provisioning, SSO/OIDC, administrator-managed system configuration and production-grade service identity remain outstanding. Keep the gateway in protected mode for human access control; the Compose default still runs as an unauthenticated local demonstration.
