# Synthetic purchase success objective

The ITOC Overview displays an SRE-style objective for the selected development or staging environment. It uses durable, **completed** `transactions` in a rolling 30-day window, queried from PostgreSQL when the overview refreshes. Processing workflows are excluded until they commit an outcome. Each committed outcome is classified by `error_code` (`domain.FailureClass`). A `SUCCESS` is good. A **business decline** (currently `INSUFFICIENT_BALANCE`) is an expected rule-based refusal: it counts as good for the SLI, does not consume error budget, and is reported separately. Every other `FAILED` outcome, including deliberate fault injection and any unclassified or empty code, is a **technical failure** and counts against the objective. Idempotent replay does not add another transaction. The target is 99.9%.

For `total = success + technical + declined`, the current SLI is `100 × (total − technical) / total`. The allowed failure budget is `total × (1 − 0.999)` failure equivalents; remaining is `max(0, allowed − technical)`, and consumed is `100 × technical / allowed`. Consumption can exceed 100% after the objective is breached. The budget is traffic-based and fractional at low volume: one technical failure may consume much more than 100% when fewer than 1,000 purchases were observed. When `total = 0`, the current SLI and budget consumption are **unknown**, never 100% or healthy.

This measures the success of the synthetic customer journey, not a contractual availability SLO for a real telecom service. Business declines no longer affect the objective, so the metric is far less sensitive to the test-traffic mix; a sudden rise in the declined share is still visible in the overview and `telcopulse:business_decline_ratio:increase1h`, and may indicate a defect worth investigating. The dashboard's one-hour success trend and the Prometheus `BusinessSuccessRateLow` alert use different windows and may disagree without either being wrong. Review transaction error codes, sample size and window before interpreting a breach. The one-hour overview also returns `technical_failed` and `business_declined`; the dashboard's success rate there remains the raw business success rate.

The Prometheus alert estimates how quickly the 30-day objective's error budget is being spent: a technical failure fraction (`transaction_total{status="FAILED",failure_class="technical"}`) above 1.44% in both 5m and 1h windows is a 14.4× fast burn; above 0.6% in both 30m and 6h windows is a 6× sustained burn. It also requires at least five terminal outcomes in the 5m window for the fast branch or thirty in the 30m window for the sustained branch. Either branch fires the same SEV-2 alert after 30 seconds, so a single firing episode creates one incident. Empty/healthy traffic remains silent. New deployments may have less history than the longer range and can still fire when the shorter window has enough outcomes. These windows use process-local Prometheus counters, not the durable 30-day ledger; a gateway crash between commit and observation can omit an outcome. The alert is an investigation signal, not an external page or a proof of customer impact.

The provisioned [Grafana operations dashboard](http://localhost:3002/d/telcopulse-operations) plots both pairs of burn-rate windows in budget multiples, with threshold lines at 14.4× and 6×. An alert may clear as recent traffic recovers while the durable 30-day SLO still reflects older failures. In local demo mode, `python3 tests/integration/slo_burn.py` starts a bounded 30-second `payment-decline` simulation, creates six durable technical failures (stopping the simulation in a `finally` block) and checks the recorded burn rate, firing alert and ingested incident; run it only against the local synthetic stack.

The API includes `purchase_slo` in `GET /api/v1/overview?environment=development|staging`, with exact start/end timestamps, counts (`failed` = `technical_failed` + `business_declined`), target, current percentage, allowed failures, remaining failure equivalents and consumed percentage. The query reads the persisted ledger; Prometheus's process-local counter is a separate operational signal and may miss increments around a crash.
