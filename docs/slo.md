# Synthetic purchase success objective

The ITOC Overview displays an SRE-style objective for the selected development or staging environment. It uses durable, **completed** `transactions` in a rolling 30-day window, queried from PostgreSQL when the overview refreshes. Processing workflows are excluded until they commit an outcome. Each committed `SUCCESS` counts as good and each `FAILED` counts against the objective, including an insufficient-balance decline or deliberate fault injection. Idempotent replay does not add another transaction. The target is 99.9%.

For `total = success + failed`, the current SLI is `100 × success / total`. The allowed failure budget is `total × (1 − 0.999)` failure equivalents; remaining is `max(0, allowed − failed)`, and consumed is `100 × failed / allowed`. Consumption can exceed 100% after the objective is breached. The budget is traffic-based and fractional at low volume: one failed outcome may consume much more than 100% when fewer than 1,000 purchases were observed. When `total = 0`, the current SLI and budget consumption are **unknown**, never 100% or healthy.

This measures the success of the synthetic customer journey, not a contractual availability SLO for a real telecom service. Expected customer declines count as failed outcomes, so the metric is sensitive to the test-traffic mix. The dashboard's one-hour success trend and the Prometheus `BusinessSuccessRateLow` alert use different windows and may disagree without either being wrong. Review transaction error codes, sample size and window before interpreting a breach.

The Prometheus alert estimates how quickly the 30-day objective's error budget is being spent: a failure fraction above 1.44% in both 5m and 1h windows is a 14.4× fast burn; above 0.6% in both 30m and 6h windows is a 6× sustained burn. It also requires at least five terminal outcomes in the 5m window for the fast branch or thirty in the 30m window for the sustained branch. Either branch fires the same SEV-2 alert after 30 seconds, so a single firing episode creates one incident. Empty/healthy traffic remains silent. New deployments may have less history than the longer range and can still fire when the shorter window has enough outcomes. These windows use process-local Prometheus counters, not the durable 30-day ledger; a gateway crash between commit and observation can omit an outcome. The alert is an investigation signal, not an external page or a proof of customer impact.

The provisioned [Grafana operations dashboard](http://localhost:3002/d/telcopulse-operations) plots both pairs of burn-rate windows in budget multiples, with threshold lines at 14.4× and 6×. An alert may clear as recent traffic recovers while the durable 30-day SLO still reflects older failures. In local demo mode, `python3 tests/integration/slo_burn.py` creates six intentional, durable declines and checks the recorded burn rate, firing alert and ingested incident; run it only against the local synthetic stack.

The API includes `purchase_slo` in `GET /api/v1/overview?environment=development|staging`, with exact start/end timestamps, counts, target, current percentage, allowed failures, remaining failure equivalents and consumed percentage. The query reads the persisted ledger; Prometheus's process-local counter is a separate operational signal and may miss increments around a crash.
