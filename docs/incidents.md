# Incident service

The [operator runbooks](runbooks/README.md) provide response and recovery checks for the eight required failure classes. Use the incident's measured environment, time window and source alert before choosing one; a linked simulation or deployment is evidence to test, not a proven cause.

The incident service owns PostgreSQL `incident.records` and `incident.audit` (migration 009). It runs independently through the shared Go runtime with service-token authentication, a separate incident mutation capability, health/readiness probes, Prometheus metrics and OTel HTTP/database tracing. Protected mode derives incident actors and roles from validated gateway sessions; the default local demo mode records `local-operator`.

## Internal API

- `POST /internal/incidents`: JSON detection envelope and editable details; requires an `Idempotency-Key` of 16–100 letters, digits, underscores or hyphens. Returns 201 on creation, 200 with the latest record on an identical replay, or 409 when the same key identifies different input/actor.
- `GET /internal/incidents?environment=development&state=Detected&limit=50`: exact environment/state, severity and service filtering; case-insensitive literal owner and title/ID search; optional RFC 3339 `since` for detection time. Owner, service and search are bounded to 100 characters. Limit is 1–100; list items are compact summaries, with investigation fields available through detail. `more` signals additional results and `next` is passed as `cursor` for the next page. `sort` accepts `updated_desc` (default), `detected_desc`, `detected_asc` or `severity_asc`; cursors retain every filter and sort. Concurrent edits can move records ahead of a cursor; refresh the first page to see live changes.
- `GET /internal/incidents/{id}`: consistent current snapshot plus up to ten audit revisions, oldest first. `history_more` and `history_next` indicate another page; pass the latter as `history_after`. Immutable revision cursors avoid duplicates when edits append between requests. Each page includes its current snapshot; pages are not a frozen cross-request database snapshot.
- `GET /internal/incidents/{id}/logs?window=24h`: optional indexed Splunk log evidence for the incident's fixed service/environment. `window` accepts `2h`, `24h` (default) or `72h` after detection, beginning fifteen minutes before detection. The response identifies whether search is configured and distinguishes zero indexed events from source failure. See [Splunk integration](splunk.md).
- `GET /internal/incidents/{id}/traces?window=24h`: optional Jaeger v3 trace evidence for the persisted incident's service and environment. It uses the same bounded detection windows as logs, preferring a purchase-operation query near detection for purchase-path incidents and falling back to a general service query when empty. It retrieves at most eight trace summaries and projects at most four matching traces. The response exposes only verified service/database nodes, observed parent edges, maximum span duration and error flags, including business failure when an instrumented span records `transaction.outcome=FAILED`; it never returns raw span attributes. Missing Jaeger configuration, no matching traces and source failure remain distinct states.
- `GET /internal/incidents/{id}/metrics?window=2h`: optional Prometheus range evidence anchored to the persisted detection time; also accepts `24h` and `72h`. Five fixed series cover environment-scoped synthetic business success and transaction rate plus affected-service shared-runtime HTTP RPS, 5xx fraction and P95 latency. The response includes UTC timestamps, units, scope, step, and empty arrays for absent samples. Browser input cannot supply PromQL or override service/environment. Prometheus retention may omit older portions of a window.
- `GET /internal/incidents/{id}/infrastructure?window=2h`: optional [Datadog container evidence](datadog.md) for the persisted incident environment/service. Three fixed metrics cover pod restarts, memory working set and CPU usage; returned namespace/pod series are bounded and rechecked against source tags. An unconfigured source, no matching measurements and source failure have distinct UI states. This is infrastructure correlation, not an automatic OOM/root-cause determination.
- `GET /internal/incidents/{id}/purchase-impact?window=2h`: observed completed synthetic purchases in the incident environment for `2h`, `24h` or `72h` from detection, starting fifteen minutes before it. Returns counts of completed, successful and failed purchases and distinct customer IDs with a failure, plus up to twenty newest failed transaction references. `more` and `next` support an opaque incident/window-scoped `cursor`. Services outside the purchase path return `applicable: false`. The projection never contains an unmasked subscriber number and does not change operator-assessed incident impact.
- `GET /internal/incidents/actions`: environment-scoped corrective-action register with status, priority, owner, literal text search and paged results. The default status is active; completed work is available explicitly. The source incident remains authoritative.
- `GET /internal/incidents/postmortems?environment=development&limit=20`: newest immutable structured reports, with optional exact `service`, exact `severity`, literal `search` and opaque `cursor`. Limit is 1–100. `more` and `next` page by report generation time and incident ID; cursors are scoped to the filters. Only generated reports appear.
- `PUT /internal/incidents/{id}`: full editable fields, desired `state`, `expected_version`, and a required audit `note`. Returns 409 on a stale version, 422 for invalid fields/transitions, and 404 for a missing record.
- `POST /internal/incidents/{id}/escalations`: `expected_version`, required `team` and `reason`, optional `owner` and `severity`. Only Incident Commander and Administrator may use it in protected mode. It increments escalation level, records the owning team and timestamp, and appends an `escalated` audit entry atomically. It cannot lower severity or escalate a Resolved/Postmortem incident.
- `POST /internal/incidents/{id}/postmortem`: `expected_version`, `summary`, `detection`, `contributing_factors`, `what_went_well`, `what_went_wrong` and an audit `note`. Incident Commander and Administrator may generate it after resolution. It atomically advances to Postmortem, stores a structured snapshot and appends a `postmortem_generated` audit revision. Stale or duplicate generation returns 409; incomplete narrative or missing recorded impact returns 422.

Requests are capped at 128 KiB and reject unknown fields and trailing JSON. Evidence accepts HTTP(S) references without credentials; URLs are stored, never fetched by this service. Rate measurements use fractions 0–1 and latency uses milliseconds. Nullable impact counts and measurements represent unknown values. Detection environment/service and original detection timestamps are immutable after creation.

## Gateway API

The same operations are exposed at `/api/v1/incidents` through the Go gateway and frontend rewrite. Mutations use existing origin protection; incident creation requires an idempotency key, while escalation requires the current incident version. The gateway uses its own service credential and incident mutation capability and never forwards browser cookies, authorization or caller-supplied actor headers. Expected validation, missing-resource and version-conflict statuses are preserved; upstream failures are masked as 503. The local Compose default remains demo mode; protected sessions can be enabled with `AUTH_REQUIRED=true`.

## Lifecycle

The forward path is Detected → Acknowledged → Investigating → Identified → Mitigating → Monitoring → Resolved → Postmortem. An owner is required after detection, root cause after identification, mitigation before monitoring, a resolution and recovery validation before resolving, and retrospective notes for postmortem. Resolving from Monitoring requires an operator observation (at least ten characters), an HTTP(S) evidence URL without credentials, and an observation time between detection and one minute after the server's current time. The incident service stamps the authenticated actor and validation time; client-supplied values cannot impersonate them. The observation and source are operator-reviewed evidence, not an automated guarantee of health. Resolved SEV-1/2 incidents must use structured generation rather than a generic state edit. Corrections may return Identified or Mitigating to Investigating; Monitoring may return to Mitigating or Investigating. Resolved may reopen to Investigating, clearing the current resolution timestamp and recovery validation while retaining both in audit history. A second resolution requires a fresh observation. Legacy resolved records can have no recovery validation; they are displayed as such. Postmortem is terminal for state changes; detail edits remain auditable.

The generated report is a separate immutable PostgreSQL document. It captures incident ID and source revision, generated time/actor, summary, recorded impact, detection, root cause, contributing factors, mitigation, resolution, learning notes, normalized action items and the complete audit timeline through generation. It is returned with incident detail as `postmortem` without depending on the ten-entry audit pagination window. Later incident detail edits do not rewrite the report. Reports generated before mitigation was added retain their original document and show that field as absent. Existing lower-severity or legacy Postmortem incidents can generate a report after the fact if one does not exist. An existing note without a structured report is shown as legacy investigation content, not presented as a completed report.

Updates lock the record, compare its revision, and commit the new snapshot and audit entry in one transaction. Every edit advances the revision, including same-state edits. Replays do not add audit entries. Database triggers reject audit UPDATE/DELETE through ordinary SQL; this is not a claim of tamper-proof storage against database administrators. Production least-privilege database roles remain part of the security phase.

## Verification and remaining work

Unit tests cover the eight-state lifecycle, reopening timestamps and missing-evidence gates. Real PostgreSQL tests cover creation replay/conflict, concurrent updates, append-only history and rollback when audit insertion fails. HTTP tests cover authentication, request bounds, filtering and rejection of client-supplied actors.

Durable alert delivery, external on-call paging, SSO, evidence retrieval and production retention remain follow-up work. The incident backend does not claim the complete incident demonstration is ready.

## Escalation coordination

Incident detail shows the current owning team, escalation level and most recent escalation time. Incident Commander and Administrator can record a handoff with a reason, optional owner assignment and equal-or-higher severity; the list also shows the owning team. The action is revision-checked, so concurrent incident edits cause a 409 and require re-review. Each escalation preserves the complete before/after snapshots and authenticated actor in the audit history. It records coordination in TelcoPulse only; it does not deliver an external page or notify the named team.

## Manual creation

The incident register can save the current state, severity, service, owner, search and detected-time filters, sort order and visible columns as a named view. Select a saved view to restore its configuration after a reload; Update view replaces its configuration or name, and Delete view removes it. Each view belongs to the authenticated operator and selected environment. In local mode, views belong to the shared `local-operator` identity. Time presets remain relative when reopened; page cursors are never saved. Up to twenty views can be saved per operator. Saved views are personal preferences, so Viewers can manage their own views without gaining incident edit rights.

The register sorts on the server by last update, newest or oldest opened time, or highest severity. Every mode uses a sort-scoped keyset cursor, so changing the order resets pagination. Opened time is indexed in a dedicated PostgreSQL column synchronized from the incident snapshot. TanStack Table manages column visibility for the bounded page; the incident identity remains visible. The table has an explicit View details action and sticky headers. On narrow screens, the table scrolls horizontally.

## Observed purchase impact

For incidents on the synthetic purchase path (gateway, subscriber, package or payment service), the detail page reads completed purchase outcomes in the incident environment from fifteen minutes before detection through the selected two-, twenty-four- or seventy-two-hour window. It reports total, successful and failed purchases, distinct customer IDs with a failed purchase, and a bounded, newest-first page of failed transactions linked to their investigation pages. Each row includes a trace ID and error code; it never returns an unmasked subscriber number. Unsupported services show an explicit scope message. Counts and the failure page are read from one PostgreSQL snapshot.

These observations are correlation evidence, not a causal attribution, an estimate of every affected customer or a replacement for the operator-assessed `affected_users` and `affected_transactions` fields. Successful/failed counts include only completed persisted synthetic purchases; processing purchases, external channels and real telecom traffic are outside this cohort. The panel does not write to incident audit history or operator-owned impact fields.

## Live recovery assessment

`GET /api/v1/incidents/{id}/recovery-assessment` compares two adjacent rolling five-minute windows of terminal synthetic purchase workflows in the incident environment, timed by workflow completion rather than original purchase creation. It evaluates only gateway, subscriber, package and payment incidents in Monitoring. The monitoring start is read from the latest audited transition into Monitoring; this also works for incidents created before the assessment feature. The query uses one repeatable-read PostgreSQL snapshot and a partial terminal-workflow time index. It does not accept a caller-supplied environment or window.

The panel calls a sample `meets_target` only after Monitoring covered both full windows, each contains at least five completed purchases, and each meets the 99.9% synthetic purchase success target. Recent Monitoring, sparse traffic and no traffic are unknown. Failed outcomes, including expected synthetic declines, remain failures. The panel shows exact counts and evaluation time and can stage a time-stamped metric summary in the audited incident editor. A healthy sample does not resolve the incident or prove recovery of unrelated traffic, dependencies, external channels or all customers. The separate human-reviewed resolution validation remains required.

The register's Create incident dialog records a Detected incident in the selected environment. Operators choose the affected service, severity, title, optional owner and impact. Unknown measurements remain unset. Each submitted command receives a creation key. On an uncertain failure the dialog locks that command and offers an exact retry; closing/reopening the dialog on the same register retains it. Keep the page open until the result is confirmed: pending commands currently live in browser memory and do not survive reload/navigation. Known validation failures unlock the form for correction.

Impact editing uses nullable counts, latency in milliseconds and rates expressed as fractions (0–1). Clearing a measurement restores unknown (`null`); entering zero records a measured zero. Counts must be nonnegative safe integers. Deployment references are operator-entered correlation identifiers, not evidence that a deployment integration is connected. Every change uses the same revision check and audit note as lifecycle edits.

## Evidence and follow-up editing

The incident editor stages up to 50 evidence references and 50 action items per incident. Evidence includes a type, summary and optional HTTP(S) URL without embedded credentials. Action items require a title and owner, P1/P2/P3 priority, and Open/In Progress/Blocked/Completed status; optional ISO 8601 deadlines include an explicit timezone. Existing done-only items are read as P2 and Open or Completed, and old commands remain accepted. New writes persist the normalized status and a compatible `done` flag derived from it. Incident Commanders and Administrators can edit action items; Operators can view them but cannot change them. Removing a row changes only the draft until Save incident commits the complete collection with an audit note and expected revision. Earlier collection values remain in immutable before/after audit snapshots. References are not fetched by the application and do not imply a connected vendor integration.

The RCA & Actions page at `/rca` lists follow-ups across incidents in the selected environment. It filters and pages on the server, places unfinished and early-due work first, marks overdue dates, and links each action to the source incident's action section. Legacy `action_items: null` records produce no rows; done-only entries display normalized values without rewriting their audit history. Editing still requires the incident's current revision and role policy. The register uses filter-scoped offset cursors over current incident documents, so concurrent edits can shift later pages; refresh before relying on an old page. Standalone action IDs and independent action ownership/audit tables are not yet implemented.

The RCA reports page at `/rca/reports` searches published structured postmortems by current incident title/service/severity and frozen report narrative. It lists frozen root cause, contributing factors, mitigation and learning notes, and links to the full report and timeline. Current incident title, service and severity are navigation metadata and may change after publication; report narrative does not. Results use filter-scoped keyset cursors, so a newly published report can appear ahead of a later page; refresh the first page to see it.

## Automatic Prometheus detection

Compose configures a ten-second incident-service poll of the [Prometheus alerts API](https://prometheus.io/docs/prometheus/latest/querying/api/#alerts). Only firing observations of the seven repository alerts are accepted: BusinessSuccessRateLow, ServiceLatencyHigh, ServiceUnavailable, NotificationConsumerLag, EventPublicationDelayed, KafkaLagMeasurementUnavailable and LogExportLoss. `BusinessSuccessRateLow` now represents either paired-window SLO burn branch under one alert identity; both branches cannot create separate incidents for a single firing episode. Business alerts retain their environment label; shared local infrastructure alerts use the configured `PROMETHEUS_ENVIRONMENT`. Invalid scopes and unknown rules cannot create arbitrary incidents.

The creation key hashes the stable source identity, complete label set and normalized activation time. PostgreSQL uniqueness deduplicates an episode across polls/process restarts. Existing incidents are returned without replacing operator fields or adding audit rows; a new activation time is a new episode. Initial audit actor is `prometheus-alert`. Detection includes metric evidence and leaves affected counts/rates unknown until assessed. Clearing a source alert does not resolve or change operator lifecycle state.

`PROMETHEUS_URL`, `PROMETHEUS_SOURCE`, `PROMETHEUS_ENVIRONMENT` and optional `PROMETHEUS_VIEWER_URL` configure ingestion. An empty endpoint disables it for native development. Requests have deadlines, no redirects, a 1 MiB response cap and a 1,000-observation cap; errors are logged and retried on subsequent polls. This is snapshot polling, not a durable notification queue: an episode that starts and ends while ingestion is unavailable can be missed. Prometheus restart behavior can also change episode activation identity. Durable alert delivery, HA grouping and escalation remain follow-up work.

## Operations overview

`GET /api/v1/incidents/overview?environment=development` returns a consistent database snapshot containing the active count, SEV-1/2 count and up to five incident summaries. Active means Detected through Monitoring; Resolved and Postmortem are excluded. Summaries are ordered by severity, latest update and ID. These are current unresolved incidents across all creation times, not a transaction-window metric. Dashboard failures display unavailable data and a retry action, never an inferred zero or healthy status.

## Live telemetry and reviewed metric evidence

Incident details reuse the service-health endpoint and display only the affected service's current measurements. Scope is shared runtime, including both transaction environments; these HTTP readings are not incident-time business impact. They never populate affected-user counts or overwrite recorded rates, latency, lifecycle state or RCA.

“Review metric evidence” copies the displayed evaluation time, scope, window, status and exact measurements into an evidence draft. The existing audited, version-checked editor reviews and saves it. Polling updates or telemetry failures cannot replace an already-open draft; an outage disables new captures. The evidence collection limit remains 50. A conflict requires the operator to discard/reload before editing again. Evidence is operator-reviewed text, not a signed telemetry attestation or a historical Prometheus series.

### Sustained HTTP latency

`ServiceLatencyHigh` detects shared-runtime service HTTP P95 above one second for thirty seconds, gated on at least twenty HTTP observations over five minutes. It creates a SEV-2 incident through the existing durable episode deduplication path. The incident environment is the configured alert-routing environment: HTTP histograms do not establish the customer environment. Evidence explicitly records that distinction, and impact measurements remain unassessed. Stopping a simulation does not immediately clear the five-minute latency window or resolve an operator incident.

The histogram quantile is an estimate between configured bucket boundaries, so HTTP P95 need not equal the configured injection delay or an individual trace duration. A payment dependency delay can fire separate gateway and payment service episodes; ingestion deduplicates each service episode, not a cross-service incident cluster. Use traces and evidence to correlate those incidents.

New automatic incident evidence links select every label from the observed alert, including service, instance and environment when present. Values are escaped, label names validated and selector order deterministic. The link queries current firing state; after recovery it can return no series. It is not historical evidence. Previously stored incident evidence remains unchanged because ingestion preserves operator-owned records and original snapshots.
